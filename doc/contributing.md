# Руководство для разработчиков (Contributing Guide)

В нашем проекте настроены строгие автоматические правила для поддержания чистоты кода, стабильности приложения и читаемости истории Git. Мы используем **Husky**, **lint-staged** и **Commitlint**.

---

## 1. Правила написания коммитов (Conventional Commits)

Все сообщения коммитов в проекте строго проверяются утилитой **commitlint**. Они должны соответствовать стандарту [Conventional Commits](https://www.conventionalcommits.org/). Если формат будет нарушен, хук `commit-msg` отклонит коммит.

### Строгий формат сообщения:

```text
<тип>: <описание со строчной буквы, без точки в конце>
```

- Описание **обязательно** начинается со строчной буквы.
- Точка в конце описания **запрещена**.
- Максимальная длина заголовка: **100 символов**.

### Доступные типы:

| Тип          | Назначение                                                                        |
| ------------ | --------------------------------------------------------------------------------- |
| **feat**     | Новая функциональность (feature)                                                  |
| **fix**      | Исправление ошибки или бага                                                       |
| **refactor** | Переписывание кода без изменения его внешнего поведения                           |
| **style**    | Исправление форматирования кода (пробелы, точки с запятой), не влияющее на логику |
| **docs**     | Обновление документации (README, CONTRIBUTING, комментарии)                       |
| **chore**    | Рутинные задачи: обновление зависимостей, настройки сборки, линтеров              |
| **test**     | Добавление или исправление тестов                                                 |
| **perf**     | Изменения кода, улучшающие производительность                                     |
| **build**    | Изменения системы сборки или зависимостей (npm, vite)                             |
| **ci**       | Изменения в настройках CI/CD (GitHub Actions, GitLab CI)                          |
| **revert**   | Откат предыдущего коммита                                                         |
| **wip**      | Work In Progress — незаконченный код, черновик (кастомный тип проекта)            |
| **hotfix**   | Срочное исправление прямо на продакшене (кастомный тип проекта)                   |

### ✅ Примеры ПРАВИЛЬНЫХ коммитов:

```text
feat: add user profile modal
fix: resolve crash on form submit
refactor: extract variable details to a shared hook
chore: update antd to version 6.4.4
wip: login form layout draft
hotfix: patch critical auth redirect
```

### ❌ Примеры НЕПРАВИЛЬНЫХ коммитов (Git их отклонит):

```text
Added new modal           → нет типа, начинается с большой буквы
fix bugs                  → нет двоеточия после типа
Refactoring               → тип с большой буквы, нет описания
fix: Resolve auth issue   → описание начинается с большой буквы
feat: add new button.     → точка в конце заголовка
```

## 2. Автоматические проверки (Git Hooks)

Под капотом репозитория работает утилита **Husky**, которая перехватывает ваши действия в Git и защищает кодовую базу на трёх уровнях.

### Хук `pre-commit` — Форматирование и линтинг

Запускается **перед созданием коммита**. Автоматически применяет `lint-staged`:

| Паттерн файла             | Действия                            |
| ------------------------- | ----------------------------------- |
| `*.ts`, `*.tsx`           | `eslint --fix` → `prettier --write` |
| `*.css`, `*.json`, `*.md` | `prettier --write`                  |

- **Важно:** проверке подвергаются **только** файлы, добавленные в индекс (`git add`). Это значительно ускоряет коммиты.

### Хук `commit-msg` — Проверка текста коммита

Запускается **после ввода сообщения коммита**, но **до его создания**. Проверяет текст на соответствие правилам Conventional Commits из раздела 1.

### Хук `pre-push` — Полная проверка проекта

Запускается **перед отправкой** веток на удалённый сервер (`git push`). Выполняет тяжёлые проверки по **всему проекту целиком**:

1. **Проверка типов TypeScript:** `npm run tsc` — проверяет все файлы проекта на корректность типизации.
2. **Запуск всех тестов:** `npm run test` — прогоняет все юнит-тесты через Vitest.

> Если во всём проекте обнаружена хотя бы одна ошибка типизации или упал хоть один тест — `git push` будет **заблокирован**. Это гарантирует, что удалённый репозиторий всегда остаётся в рабочем состоянии.

## 3. Переменные окружения

Переменные окружения настраиваются в файле `.env` в корне проекта. Файл `.env.example` содержит шаблон с безопасными значениями по умолчанию.

| Переменная          | Описание                               | По умолчанию                |
| ------------------- | -------------------------------------- | --------------------------- |
| `VITE_API_URL`      | Базовый URL API-сервера                | `http://localhost:3000/api` |
| `VITE_APP_TITLE`    | Заголовок приложения                   | `React Template App`        |
| `VITE_AUTH_ENABLED` | Включить/отключить систему авторизации | `false`                     |
| `VITE_I18N_ENABLED` | Включить/отключить мультиязычность     | `false` (фолбэк на `ru`)    |

> **Feature Flags:** Авторизация и i18n контролируются через переменные окружения. Если `VITE_AUTH_ENABLED=false`, все защищённые маршруты автоматически открыты для всех, а гостевые маршруты (`/login`, `/register`) перенаправляют на главную.

## 4. Полезные npm-скрипты

| Команда              | Описание                                          |
| -------------------- | ------------------------------------------------- |
| `npm run dev`        | Запуск dev-сервера (Vite, HMR)                    |
| `npm run build`      | Production-сборка (TypeScript check + Vite build) |
| `npm run tsc`        | Проверка типизации TypeScript (без сборки)        |
| `npm run lint`       | Запуск ESLint по всему проекту                    |
| `npm run format`     | Запуск Prettier по всем файлам в `src/`           |
| `npm run test`       | Запуск всех тестов (Vitest, однократный прогон)   |
| `npm run test:watch` | Запуск тестов в watch-режиме (Vitest)             |
| `npm run preview`    | Превью production-сборки (из `dist/`)             |

## 5. Экстренный обход правил (Не рекомендуется!)

Мы категорически не рекомендуем обходить проверки, так как это нарушает стандарты проекта. Однако, если вам нужно экстренно сохранить незаконченный код в свою ветку (например, в конце рабочего дня), вы можете отключить Husky флажком `--no-verify` (или `-n`):

```bash
git commit -m "wip: draft save" --no-verify
git push --no-verify
```

> **Внимание:** на сервере в CI/CD (если он настроен) такие коммиты всё равно могут упасть.
